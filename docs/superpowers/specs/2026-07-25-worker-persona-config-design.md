# Worker Persona Externalization — Technical Specification

**Version:** 1.0 (design/spec — no implementation yet)
**Date:** 2026-07-25
**Author:** Mohan Sagar K
**Status:** Approved design, ready for implementation

> Follow-up to the Leo response-tone work, deliberately deferred out of that spec. The persona
> (`defaultPersona` in `worker/src/config.ts`) is currently Mohan's real name, bio, and facts
> hardcoded in source. This slice makes it configurable via environment, with a generic placeholder
> shipped in source and Mohan's real data supplied only through his own local/production config —
> curated in this same slice from `portfolio-data`, his separate content repo
> (`/Users/mohansagar/Documents/portfolio-data`).

---

## 1. Goal

Anyone who forks or clones this repo to run their own version of the bot currently inherits
Mohan's real name, employers, and career history baked into `worker/src/config.ts`. This slice makes
`Persona` loadable from a single environment variable, with the source-committed default becoming a
clearly generic placeholder — and separately, curates Mohan's own real persona (drawn from
`portfolio-data`) into his own local (`.dev.vars`) and production (`wrangler.toml`) config, matching
how every other environment-specific value (`ALLOWED_ORIGINS`, `MODE`, etc.) is already handled.

---

## 2. Locked Decisions

| # | Area | Decision |
|---|------|----------|
| P1 | Data sourcing | Static config snapshot, not a live fetch from `portfolio-data` at runtime. No new network dependency in the chat path; no risk of the persona changing mid-conversation or failing if GitHub is briefly unreachable. Future re-syncs (if Mohan's `portfolio-data` changes) are a manual edit to his local config — no auto-sync tooling in this slice. |
| P2 | Config mechanism | One new env var, `PERSONA_JSON`, holding the entire `Persona` object as a JSON string — not a dozen scalar vars (`OWNER_NAME`, `BIO`, ...). Parsed once in `loadConfig(env)`, shallow-merged over `defaultPersona` so a partial override doesn't drop required fields. Matches the existing `loadConfig(env)` pattern (`MODE`, `TTS_VOICE`, etc. already come from `env`). |
| P3 | Shipped default | `defaultPersona` in source becomes a generic placeholder (invented facts, no real employers/numbers/achievements) — not Mohan's real resume. Bot name (`Leo`) and owner-name style stay as an illustrative example, matching the widget's own `DEFAULTS.branding.botName: "Leo"` convention, but the substantive content (bio, facts, tone) is genericized. |
| P4 | Mohan's real config | Lives only in `worker/.dev.vars` (local, already gitignored) and `worker/wrangler.toml`'s `[vars]` (production) — following the exact existing pattern for `ALLOWED_ORIGINS`, which is already Mohan-specific and already committed there. Not treated as a secret: it's the same public info already on his live portfolio site. |
| P5 | Content curation | Mohan's `facts[]`/`bio` are hand-curated once now (this slice), by reading `portfolio-data`'s `profile.json`, `experience.json`, `skills.json`, `achievements.json`, `education.json` — not auto-generated by a script. Concrete content is part of this spec (§4), not left to implementation. |
| P6 | Generic-instruction cleanup | `buildSystemPrompt`'s hardcoded parenthetical — `"(he's a sharp, hands-on problem-solver who genuinely loves the hard stuff)"` — is describing Mohan specifically inside otherwise-generic instructional text. Removed; the instruction relies on `tone`/`facts` alone to let the model "talk him up in fresh words," which the existing transcripts show it already does without needing a canned example baked in. |
| P7 | Scope boundary | `Persona`'s shape is unchanged (`botName`, `owner{name,role}`, `bio`, `tone`, `facts[]`, `do_not[]`) — no new fields beyond what's needed. No changes to `graph.ts`, `nodes.ts`, `providers.ts`, or any widget file. No auto-resync script/tooling (P1). No live-fetch integration with `portfolio-data`'s API. |

## 3. `worker/src/config.ts` — env-driven persona

```ts
export interface Env {
  // ...existing fields unchanged...
  PERSONA_JSON?: string;
}

function loadPersona(env: Env): Persona {
  if (!env.PERSONA_JSON) return defaultPersona;
  try {
    const parsed = JSON.parse(env.PERSONA_JSON) as Partial<Persona>;
    return {
      ...defaultPersona,
      ...parsed,
      owner: { ...defaultPersona.owner, ...(parsed.owner ?? {}) },
    };
  } catch {
    return defaultPersona; // malformed override — fail safe to the shipped default, don't crash the worker
  }
}

export function loadConfig(env: Env): AppConfig {
  return {
    defaultProvider: env.DEFAULT_PROVIDER || "groq",
    providers,
    persona: loadPersona(env),
    // ...rest unchanged...
  };
}
```

`defaultPersona` changes from Mohan's real data to a generic placeholder:

```ts
export const defaultPersona: Persona = {
  botName: "Leo",
  owner: { name: "Alex", role: "Software Engineer" },
  bio: "A software engineer who enjoys building things and solving interesting problems.",
  tone: "warm, a little playful, and genuinely curious — a friendly guide, never a corporate bio",
  facts: [
    "Alex works across full-stack development and enjoys tackling hard technical problems.",
    "Alex is open to freelance projects and full-time roles.",
  ],
  do_not: ["quote prices", "commit to dates", "schedule meetings"],
};
```

`buildSystemPrompt`'s line 10 changes from:
```ts
`- Lead with personality, NOT a résumé. If someone asks "who is ${p.owner.name}?", don't recite his job title like a LinkedIn bio — talk him up warmly in your OWN fresh words (he's a sharp, hands-on problem-solver who genuinely loves the hard stuff), and only give specifics if they want them.`,
```
to:
```ts
`- Lead with personality, NOT a résumé. If someone asks "who is ${p.owner.name}?", don't recite his job title like a LinkedIn bio — talk him up warmly in your OWN fresh words, grounded in his actual facts and tone below, and only give specifics if they want them.`,
```

No other file changes. `Persona`'s type shape, `buildSystemPrompt`'s signature, and every call site
(`nodes.ts`) are unchanged.

## 5. Testing

| Layer | Approach |
|-------|----------|
| `config.ts` | `loadConfig` with no `PERSONA_JSON` returns `defaultPersona` unchanged (existing behavior, now via the generic placeholder). `loadConfig` with a valid `PERSONA_JSON` returns the parsed override, deep-merged for `owner`. `loadConfig` with malformed `PERSONA_JSON` (invalid JSON) falls back to `defaultPersona` without throwing. A partial override (e.g. only `facts` provided) still has a valid `botName`/`owner` from the default (merge, not replace). |
| `prompts.ts` | Existing tests already assert against `buildSystemPrompt(defaultPersona)`'s content by pattern/structure, not by asserting the specific string `"sharp, hands-on problem-solver"` — confirmed no existing test breaks from removing that phrase (only Mohan's real curated persona, §4, isn't unit-tested at all, matching how persona *content* was never unit-tested before either — only the prompt-building *mechanism* is). |

No test asserts against Mohan's real curated persona content (§4) — it never ships in the repo's
default and isn't loaded during tests; it only exists in Mohan's own untracked `.dev.vars` and his
`wrangler.toml`.

---

## 6. Out of Scope (→ later, if ever)

- Auto-resync tooling that regenerates `PERSONA_JSON` from `portfolio-data` on a schedule or via a
  script (P1) — future re-syncs are manual edits.
- Live runtime fetch from `portfolio-data`'s raw GitHub URLs (P1, rejected approach).
- Any change to `Persona`'s shape, `graph.ts`, `nodes.ts`, `providers.ts`, or widget files.
- Surfacing `achievements`/`education`/`projects`/`testimonials`/`services` beyond what's already
  folded into the curated `facts[]` (§4) — the full raw `portfolio-data` corpus is not wired in.

---

## 7. Risks

| # | Item | Mitigation |
|---|------|------------|
| R1 | A malformed `PERSONA_JSON` (typo'd JSON, e.g. after a manual edit) could crash the worker on every request if unhandled | `loadPersona` catches parse errors and falls back to `defaultPersona` (§3) rather than throwing — worst case is a generic-sounding bot, never a hard failure. |
| R2 | `wrangler.toml`'s `[vars]` are committed to the repo — Mohan's curated persona (§4) becomes publicly visible in git history once added there | Accepted: this is the same public info already on his live portfolio site and in the public `portfolio-data` repo; no different in sensitivity from `ALLOWED_ORIGINS` (his domains) already being committed there. |
| R3 | Hand-curated content (§4) will drift from `portfolio-data` as Mohan's real experience/skills change over time | Accepted per P1/P5 — explicitly a manual-update model, not automated. A future spec could add resync tooling if this becomes a real maintenance burden. |
